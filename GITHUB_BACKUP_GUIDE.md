# Backing up FPGA/HACC work to GitHub so a cluster wipe costs you nothing

**Who this is for.** You (or your Claude) are working on an operator in the celeris/oasis stack on the
ETHZ HACC cluster. Your home directory **will** be wiped. This document is the procedure we used to
make that a non-event, including the four traps that nearly cost us files even though `git status` was
clean every time.

**Give this whole file to Claude and say: "do this for my repos."** It is written to be executed.

> **The one-line summary.** `git status` being clean does **not** mean your work is saved. Four
> categories of file are invisible to it: files matched by `.gitignore`, files inside submodules,
> files in submodules you cannot push to, and files too large for a normal push. Every one of those
> bit us. The procedure below finds all four.

---

## 0. What you are actually protecting

Do an inventory *before* touching git. In our case the code was the least of it:

| category | examples | in git? |
|---|---|:--|
| source | RTL, host C++, extension code | ✅ obviously |
| **docs & notes** | resume/handoff docs, per-test write-ups, reports | ✅ **the highest-value files you own** |
| **benchmark harnesses** | generators, sweep scripts, gate scripts | ✅ |
| **results** | result CSVs, manifests | ✅ |
| **raw run logs** | the actual terminal output behind every number in the paper | ✅ ← was `.gitignore`d |
| **paper artefacts** | figure scripts, generated PDFs, LaTeX tables | ✅ |
| **build evidence** | timing/utilisation reports for the shipped bitstream | ✅ ← was `.gitignore`d |
| **P&R / tooling scripts** | the sweep harnesses that produced the final result | ✅ ← was `.gitignore`d |
| editor workspace | `*.code-workspace` | ✅ cheap, reproduces your exact tree |
| **submodule patches** | changes to third-party submodules you cannot push | ✅ **as `.patch` files** |
| bitstreams | `*.bit`, 40–70 MB each | ⚠️ LFS, or accept re-synthesis |
| datasets | `~/datasets/*.parquet`, several GB | ❌ regenerate from scripts |
| build dirs | `build/`, `hardware/build-NN/`, `.Xil/` | ❌ regenerate |
| install prefix | `~/opt` | ❌ rebuild |

**The rule that decides it:** *if losing this file costs more than an hour to reproduce, and it is
under 100 MB, it goes in git.* A 4 GB dataset regenerated by a 30-line script is not worth storing.
A 3 KB log file that is the sole evidence behind a number in your paper absolutely is.

## 1. Find out what you can actually push to

Do this first — it determines everything else.

```bash
gh auth status                       # are you authenticated, and with what scopes?
cd ~/oasis && git remote -v          # where does origin point?
git push --dry-run origin HEAD       # can you actually write there?
```

Our result: `meminyaksi` had **READ-only** on both `celeris-labs/oasis` and `celeris-labs/celeris`, so
every `git push origin` failed with **403**. Being an org member is not write access. Check rather
than assume — a 403 discovered on wipe day is a disaster; discovered today it is a five-minute detour.

### If you have no write access, do NOT fork publicly

We considered it and rejected it deliberately:

* A public fork **publishes unpublished paper material** — draft write-ups, unreleased measurements,
  figures. Once public, forks and caches persist even after you delete.
* **private → public is reversible; public → private is not.**

Use **private personal repos** as an additional remote instead.

---

## 2. Create the backup repos and wire them as a SECOND remote

Never replace `origin`. Add a remote called `backup` beside it, so the day write access arrives, the
work moves upstream with one command and no rewiring.

```bash
# one per repo you care about
gh repo create <you>/oasis-backup   --private
gh repo create <you>/celeris-backup --private

cd ~/oasis
git remote add backup https://github.com/<you>/oasis-backup.git
git push -u backup $(git branch --show-current)

cd ~/celeris
git remote add backup https://github.com/<you>/celeris-backup.git
git push -u backup $(git branch --show-current)
```

Verify:

```bash
git remote -v
#   backup  https://github.com/<you>/oasis-backup.git   (fetch/push)   <- yours, writable
#   origin  https://github.com/celeris-labs/oasis.git   (fetch/push)   <- theirs, read-only
```

### ⚠️ You almost certainly need TWO repos, not one

Our `oasis` repo contains `celeris` as a **submodule** — but pinned at an *older* commit than the
`~/celeris` working tree, which was 4 commits ahead. Restoring `oasis` alone would have silently given
us a stale hardware tree. Check this on your side:

```bash
cd ~/oasis && git submodule status | grep celeris     # the pinned SHA
cd ~/celeris && git log --oneline -1                  # what you actually have
```

If they differ, **both repos must be backed up separately.**

## 3. 🚨 THE BIG ONE: `.gitignore` silently drops files from a staged directory

This is the trap that matters most, it bit us **twice**, and `git status` shows nothing wrong.

`git add <dir>` walks the directory and **skips ignored contents without a word**. No warning, no
error, exit code 0. You then commit, see a clean tree, and believe the directory is saved.

Two real examples from our repo:

```gitignore
build*      # intended: the hardware/build-NN/ output directories
*.log       # intended: noisy tool logs
```

* A pattern with **no slash matches at any depth, and matches FILES as well as directories.** So
  `build*` matched `hardware/pnr/evidence/build-29-analysis.txt` — the timing evidence for the shipped
  bitstream, cited in the paper. Staged the directory, committed, file gone.
* `*.log` swallowed `bench/e2e_sweep_*.log` and `report_*.log` — **the raw runs behind every number in
  the report**, 110 KB total, irreplaceable without re-running on hardware.

### The audit — run this in every repo, before you trust any backup

```bash
# 1. What is being ignored that you might actually want?
git ls-files --others --ignored --exclude-standard \
  | grep -Ev '\.(o|d|so|a|jou|str|pb|dcp)$' \
  | grep -Ev '(^|/)(build|\.Xil|node_modules|__pycache__)/' \
  | sort | head -100
```

Read that list with your own eyes. Anything that is evidence, a script, a doc, a result, or a log
behind a published number gets force-added:

```bash
git add -f hardware/pnr/evidence/ bench/*.log report_*.log
```

```bash
# 2. AFTER adding, verify with ls-files -- NOT with `git status`
git ls-files hardware/pnr/ | wc -l      # is the count what you expect?
git ls-files bench/ | grep '\.log$'     # did the logs actually land?
```

> **`git status` tells you about the working tree. `git ls-files` tells you what is in the repo.**
> Only the second one answers "is my work saved?"

What we rescued this way, all of which would otherwise have died with the cluster: the four P&R sweep
harnesses that drove our entire timing-closure arc, the build-29 timing/utilisation/directive
evidence, ~110 KB of raw benchmark logs, and a directory of worst-path reports.

## 4. Submodules: your repo saves a pointer, not the contents

A submodule is stored in your repo as **one line: a commit SHA**. If that commit only exists in your
local clone, or in a repo you cannot push to, **the code is not backed up.**

Ask, for each submodule: *do I have local modifications, and can I push them anywhere?*

```bash
cd ~/oasis
git submodule status --recursive        # SHA + path for every submodule, at every depth
git submodule foreach --recursive 'git status --short'    # any local modifications?
```

Our chain was four deep: `oasis → parcore → libstf → coyote`, and `coyote` points at **third-party
`fpgasystems/Coyote`**, which we cannot push to under any circumstances.

### The fix: pin the SHAs, and store modifications as patch files

Create a `patches/` directory at the top of your repo containing three things:

**(a) `patches/SUBMODULE-PINS.txt`** — the exact commit of every submodule at capture time:

```bash
{ echo "# Submodule chain — exact commits (captured $(date +%Y-%m-%d))"
  echo
  echo "$(basename $PWD) @ $(git rev-parse HEAD) [$(git branch --show-current)]"
  git submodule status --recursive
} > patches/SUBMODULE-PINS.txt
```

Why: a drift anywhere in a four-deep chain has cost us days. This file makes a wrong checkout
detectable in seconds instead of after a nine-hour synthesis.

**(b) One `.patch` per modified submodule:**

```bash
cd parcore/libstf/coyote
git diff > ~/oasis/patches/coyote-<what-it-changes>.patch
git diff --stat            # record this in RESTORE.md so the patch can be verified after applying
```

**(c) `patches/RESTORE.md`** — the instructions. Ours covers: clone + `git submodule update
--init --recursive`, verify against the pins, apply each patch with the expected `--stat` output, then
a table of what is *not* in git and what it costs to rebuild (bitstreams: overnight re-synthesis;
datasets: minutes; `~/opt`: one cmake).

**Write down WHY each patch matters, not just what it does.** Ours adds an environment-variable
override for a Vivado placer directive. That sounds trivial. It is worth **+0.338 ns of WNS**, and
without it the ML placer silently picks a different directive and you re-measure a wrong answer after
a nine-hour build. A future reader who does not know that will skip the patch.

## 5. Large binaries: LFS, or an honest decision not to

A bitstream is 40–70 MB. GitHub warns above 50 MB and hard-rejects at 100 MB.

```bash
git lfs install
git lfs track "hardware/build-29/bitstreams/cyt_top_b29_po.bit"
git add .gitattributes
git add -f hardware/build-29/bitstreams/cyt_top_b29_po.bit   # -f: `build*` ignores it
git commit -m "backup: production bitstream via LFS (DROP THIS COMMIT before any upstream PR)"
git push backup HEAD
```

Two rules:

* **Track the specific file, not `*.bit`.** You do not want fifteen experimental builds in LFS.
* **Say in the commit message that it must be dropped before any upstream PR.** A 43 MB LFS object is
  fine in a private backup and unacceptable in a real pull request. Write it down; you will forget.

Restoring needs `git lfs pull` after cloning — put that in `RESTORE.md`.

If LFS is unavailable, that is fine: record the bitstream's **md5 and exact build config** in a text
file so you can prove a re-synthesised one is equivalent, and accept the overnight rebuild.

## 6. 🔬 Verify by ACTUALLY RESTORING — do not skip this

A backup you have not restored is a hypothesis. Test it in a scratch directory:

```bash
cd /tmp && rm -rf restore-test && mkdir restore-test && cd restore-test
git clone -b <branch> https://github.com/<you>/oasis-backup.git oasis
cd oasis && git submodule update --init --recursive && git lfs pull
```

Then check, concretely:

```bash
ls *.md patches/ bench/                          # every doc and harness present?
md5sum hardware/build-*/bitstreams/*.bit         # matches the original?
python3 bench/paper_figs.py                      # do the figures regenerate with NO datasets present?
diff <(cd ~/oasis && git ls-files) <(git ls-files)   # same file list?
```

That last one is the real test: **the figure script must regenerate every figure from embedded data,
with no datasets on disk.** If it needs 4 GB of parquet you do not have after a wipe, your paper
figures are not actually recoverable.

We ran exactly this. Result: every doc present, bitstream md5-identical, all figures regenerated
clean. Only then did we call it backed up.

## 7. Leave a note your future self will actually find

After a wipe you will have a fresh shell and no memory of any of this. Put a **banner at the very top
of your main resume/handoff doc** — before the technical content — containing:

* which repos exist, what is in each, and **why both are needed**
* the exact `git clone` commands including branch and `--recursive` and `git lfs pull`
* a pointer to `patches/RESTORE.md`
* what is *not* in git and how to rebuild it
* the `.gitignore` warning, so you do not re-lose the same files
* a line confirming recovery was verified, and when

Ours is ~40 lines at the head of `compact.md`. It is the single highest-value thing in the repo,
because it is what turns "the files exist somewhere on GitHub" into "I am working again in 20 minutes."

## 8. Ongoing discipline

```bash
# after every working session, in each repo:
git add -A
git ls-files --others --ignored --exclude-standard | grep -Ev '(^|/)(build|\.Xil)/' | head   # anything precious being ignored?
git commit -m "..."
git push backup $(git branch --show-current)
```

* **Push at the end of every session.** The wipe will not announce itself.
* **Never trust a clean `git status`** as evidence that a directory was saved — check `git ls-files`.
* **Re-run the ignored-files audit whenever you add a new output directory.** A new `results/` or
  `evidence/` folder is exactly where a broad ignore pattern strikes next.
* Keep `patches/SUBMODULE-PINS.txt` refreshed whenever a submodule moves.

---

## 9. When write access to the real repo arrives

Because `origin` was never touched, it is one command per repo:

```bash
cd ~/oasis   && git push origin $(git branch --show-current)
cd ~/celeris && git push origin $(git branch --show-current)
```

Before that push: drop the LFS bitstream commit, and consider whether the `patches/` directory belongs
upstream (the pins probably do not; `RESTORE.md` might).

---

## 10. Checklist

- [ ] `git push --dry-run origin HEAD` — do you actually have write access? (Do not assume.)
- [ ] Backup repos created **private**; `backup` remote added **beside** `origin`, not replacing it.
- [ ] Checked whether your submodule pin differs from your sibling working tree ⇒ how many repos.
- [ ] Ran the ignored-files audit and force-added every precious ignored file.
- [ ] Verified with `git ls-files <dir>`, not `git status`.
- [ ] `patches/SUBMODULE-PINS.txt` written.
- [ ] Every modified submodule captured as a `.patch`, with **why it matters** written down.
- [ ] `patches/RESTORE.md` written, including what is *not* in git and its rebuild cost.
- [ ] Large binaries in LFS with a "drop before upstream" note, or a documented decision not to.
- [ ] **Fresh clone performed**, checksums compared, figures regenerated without datasets.
- [ ] Recovery banner at the top of the main resume doc, and pushed.
- [ ] `git status` clean and `git log origin/<branch>..HEAD` empty on the `backup` remote.
